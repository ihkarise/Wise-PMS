# Appointment System — Specification

> **Status:** Design only (Phase 2). Not implemented. Planned tables:
> `appointments`, `doctor_schedules` (+ `queue`, see
> [`WAITING_QUEUE.md`](./WAITING_QUEUE.md)). **Last updated:** 2026-07-20.
> Extends [`../docs/modules/Appointments.md`](../docs/modules/Appointments.md).

## 1. Purpose

Booking and scheduling: an appointment calendar, online booking, tokens, drop-in
and drop-off handling, Google Meet for remote visits, doctor schedules, multiple
locations, and reminder integration. The existing `visits.followup_date` is the
seed; Appointments generalizes it into forward booking with status.

## 2. Scope (charter checklist)

| Capability | Notes |
| ---------- | ----- |
| **Appointment Calendar** | Day/week view of booked slots per doctor/location |
| **Waiting Queue** | Live token board for the day — see [`WAITING_QUEUE.md`](./WAITING_QUEUE.md) |
| **Token System** | Sequential token on check-in |
| **Drop-in** | Walk-in without prior booking → assigned a token |
| **Drop-off** | Patient leaves samples/reports without a full visit |
| **Online Booking** | Patient self-books (via Portal/link) → confirmation |
| **Google Meet** | Remote appointment spawns a Meet link (Telemedicine) |
| **Doctor Schedule** | Working hours, breaks, off-days per doctor |
| **Multiple Locations** | Location dimension on schedules/appointments |
| **Reminder Integration** | WhatsApp confirmation + reminder |

## 3. Data model (planned — needs F1)

```
appointments
  id · patient_id FK · doctor_id · location_id (nullable) ·
  scheduled_at · duration_min · channel (in_person|online) ·
  status (booked|confirmed|checked_in|in_consult|done|no_show|cancelled) ·
  source (reception|online|drop_in) · meeting_link (nullable) ·
  notes · created_at · updated_at

doctor_schedules
  id · doctor_id · location_id (nullable) · weekday · start_time · end_time ·
  slot_min · active

# queue table: see WAITING_QUEUE.md
```

- `doctor_id` today is the acting user (doctor not yet a modeled entity, L3); the
  schema leaves room to promote doctor to a real entity later.
- `location_id` is nullable so a single-location clinic ignores it; multi-clinic
  scoping (a future `clinic_id`) layers on by migration (Constitution Art. VIII §5).

## 4. Status lifecycle

```
booked → confirmed → checked_in → in_consult → done
   │         │            │
   ├─────────┴────────────┴──► cancelled
   └──────────────────────────► no_show   (past scheduled_at, never checked in)
```

- **check_in** creates a queue token (see Waiting Queue).
- **in_consult** is set when the doctor opens the Consultation Workspace for that
  patient; **done** on Complete Visit.

## 5. Service contract (target)

```
appointments.service
  book(patient_id, doctor_id, scheduled_at, channel, location_id, user_id) -> int
  reschedule(appointment_id, new_time, user_id) -> None
  cancel(appointment_id, user_id) -> None
  check_in(appointment_id, user_id) -> int          # → queue token
  mark_no_show(appointment_id, user_id) -> None
  day_schedule(doctor_id, date, location_id=None) -> list[dict]
  available_slots(doctor_id, date, location_id=None) -> list[slot]
```

`available_slots` is computed from `doctor_schedules` minus booked appointments.
All mutations audited.

## 6. Integrations

| With | For |
| ---- | --- |

| **WhatsApp** | `appointment_confirmation`, `reminder` (`{appointmentDate}`) |

| **Dashboard** | "today's schedule", no-show counts |
| **Timeline** | appointment events |
| **Analytics** | no-show rates, utilization |

## 7. Reminder loop

Booking → `appointment_confirmation`; a scheduled reminder before the slot →
`reminder`. Follow-up appointments are seeded from `visits.followup_date`. See
[`WHATSAPP_SYSTEM.md`](./WHATSAPP_SYSTEM.md).

## 8. Online booking & Google Meet

- **Online booking** comes through the Portal/API (a late module) writing an
  appointment with `source = online`, `status = booked` for staff confirmation.
- **Google Meet** links are generated by the Telemedicine module behind a provider
  interface (credentials in Settings/env). See
  [`../docs/modules/Telemedicine.md`](../docs/modules/Telemedicine.md).

## 9. Dependencies & sequencing

- **Requires:** F1 (tables), F3 (RBAC so Reception owns booking). References
  existing `patients` and the acting doctor.
- **Feeds:** Waiting Queue, WhatsApp, Telemedicine, Dashboard, Analytics.
- **Sequencing:** in-clinic calendar + queue + tokens first; online booking + Meet
  after Portal/Telemedicine.

## 10. Manual test checklist (implementing phase)

- [ ] Booking respects doctor schedule and avoids double-booking a slot.
- [ ] Check-in transitions status and creates a queue token.
- [ ] Drop-in creates a same-day appointment + token.
- [ ] No-show is set for past, un-checked-in appointments.
- [ ] Confirmation/reminder WhatsApp fires (if enabled).
- [ ] Multi-location schedules resolve correctly; single-location ignores it.
- [ ] Model/table parity + router contract green.

## 11. Risks

- **Doctor entity gap (L3)** — schedules key off the acting user until a real
  doctor entity exists; design so promoting it later is additive.
- **Slot/timezone correctness** — dates are string-based today (L2); appointments
  need proper date/time handling (pairs with F5).
